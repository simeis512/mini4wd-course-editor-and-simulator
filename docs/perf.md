# パーツ追加の性能計測 (#87)

## 結果と環境

2026-10-24 (JST)、Intel Core i5-14400F、Windows x64、Node v24.16.0、Chrome 155.0.0.0で計測。
ブラウザは同じ開発サーバー・通常のウィンドウ (1209 × 535 CSS px) を使用した。
測定前は main `cb0c953` に計測だけを追加した `0b10e64`、測定後は `dff2093`。

支柱を含む接触チェックと、3Dで再計算していた支柱がLの主な負荷だった。
Lのrefreshは2Dで4765.9 → 235.9ms、3Dで4429.7 → 225.1ms。
Sは2D/3Dとも10ms以内になった。Lの50ms/16ms目標は未達であり、末尾に残る負荷と次の手を記す。

## 再現方法

- `npm run bench`：Vitest 5のtest-contextのbenchを使うNodeベンチ。各関数をwarmup 3回、測定20回。`--reporter=json --outputFile=<file>`で統計も保存できる。
- `npm run dev`で開き、URLのハッシュより前に`?perf`を追加する。コンソールの表とDevTools PerformanceのUser Timingに`mini4wd:layout`などが出る。通常のURLではmark/measure/logを実行しない。
- 開発時だけ`?perf&bench`にすると「S/M/Lを計測 (#87)」ボタンが出る。アプリ自身のload/commitとパレットのpointermove経路を動かす。各条件の最初の5回を捨て、20回の中央値を画面にJSONで出す。本番ビルドにはこのハーネスを含めない。
- 個別のpointermoveでは`dropJoin`、`preview:setData`、`pointermove`を記録する。

今回の比較ではViteを`configFile: false`、`cacheDir: 'node_modules/.vite-perf'`、
`optimizeDeps: { noDiscovery: true, include: [] }`、`server: { host: '127.0.0.1', port: 5174 }`で起動し、
`http://127.0.0.1:5174/?perf&bench`を使用した。アプリとコースのコードは上記コミットのまま。

固定コースは`src/course/bench-courses.ts`。Sは`basicOval()`の14ピース。
Mはchainから作る60ピースの閉じた立体オーバルで、ストレート・ウェーブ・カーブ・レーンチェンジ・上り/下りスロープを含む。
LはMを床・220mm上・440mm上に置き、上段の一つを90°回して交差させ、20ピースのオーバルとホース・箱を足した200ピース。
高さや配置はベンチの固定条件であり、新しいパーツの仕様値ではない。
各コースの最初のストレートを取り除き、その開いた口に1ピースを戻す。乱数は使わない。

## 採った変更と互換性

- worldTracksとsupportsをLayout単位のWeakMapで共有する。新しい編集では新しいLayoutを作り、結果は読み取り専用として使う。コース自体はキャッシュしない。明示したtracks配列が違えば支柱は再計算する。
- 支柱の路面探索を270mmの空間格子で絞り、既存のポリゴン・高さの判定をそのまま使う。脚の候補が重複して調べる横位置も再利用する。既に置いた支柱の輪郭・フレームを保持し、遠い支柱を除外する。
- 干渉チェックは各サンプルの判定範囲から保守的な境界箱を作り、重ならない干渉/クリアランス判定を除外する。点の判定・列挙順・許容値は維持する。
- EditorViewにbeginUpdate/endUpdateを加え、1回のrefreshでの2D描画と3D更新をまとめる。非表示の2Dキャンバスは描画せず、2D描画の頂点ごとのDOMサイズ読み取りをなくす。
- パレットの接続候補は1ドラッグ中に再利用する。同じ候補/スナップ位置のプレビューは描き直さず、コースやビューが変わったら更新する。
- 3Dで毎回作り直す支柱・付属物・置き物・選択輪郭のgeometryを解放する。共有する路面geometryとmaterialは保持する。全ピースのMesh生成そのものは引き続き行う。

最適化前にS/M/Lの追加前後のworldTracks・支柱・高さ・干渉・接触・周回・保存バイト列・URLを採取し、goldenテストで同一性を確認した。
傾斜・ねじれ・複数トラックが密集した3つの固定seedのコースについても、旧実装から採取した干渉結果 (座標と順序を含む) と一致する。
既存のテストも含め310テストが通過し、`npm run build`も通過。
ブラウザでクリック追加、口への接続、テンプレート追加と1回でのUndo、Redo、実際のドラッグ&ドロップ、2D/3D切替、URL再読込による復元を確認した。
`?perf`なしの通常表示では計測ログとエラーが出ないことも確認した。

## 差分更新 (#92)

### 更新方法と結果の一致

- `changedPieces` はパーツ・形状・配置行列を厳密に比較する。変わらない `WorldTrack` と2Dの外形を共有する。色や付属物だけの変更では路面を無効化しない。
- 支柱の路面格子は、削除・変更したトラックを除き、追加したトラックのセルだけをコピーして更新する。各トラックが実際に調べたセル（空だったセルも含む）を保持する。
- 支柱は従来の低い路面順に処理する。脚の探索範囲と、重複を調べた支柱フレームに影響する既存支柱が変われば再計算する。これにより、支柱の変化は後続の支柱へ伝わる。再計算して同じ支柱になった所で同じオブジェクトを保持し、伝播を止める。候補を置けなかったトラックも依存関係を保持する。
- 接触チェックは変わらない路面・支柱・置き物の形と形どうしの結果を再利用し、従来の列挙順で結果を組み立てる。
- 3Dはピースと支柱のMeshをピース単位で保持する。色・付属物・形・配置が変わったMeshだけを差し替え、不要なgeometryを解放する。スタート・タイマー・床の置き物も設定と配置が同じ間は保持する。
- 初回の `planDrop` は既存の配置を共有し、足すピースだけを配置する。接続・ループ閉じ・警告は全体で再判定し、候補の優先順位を保つ。テンプレートの持ち上げや自作ストレートの長さ合わせも従来の計算を使う。

`performance.test.ts` と `clash-bounds.test.ts` の既存スナップショットは変更していない。
S/M/Lで追加・削除・移動・反転・ねじれ・Undo相当の逆更新を全体計算と比較し、支柱・接触点・順序が一致することを確認した。
積み重なった路面の下を動かすケース、置き物・タイマーの変更、明示したtracksの差し替えも比較する。
3DのテストではMeshの同一性、全体生成と同じ頂点・配置、色・付属物・スタート・タイマーの変更、geometryの解放を検証する。
全328テスト・`npm run build`・`npm run bench` が通過。

支柱をピース単位のMeshに分けたためdraw call数は増える。今回も同期CPU処理の計測であり、GPUの描画時間やモバイル端末のフレームレートは測っていない。

## 干渉チェックの差分化 (#101)

2026-10-25 (JST)、Linux x64 のクラウド環境（AMD EPYC 9V74、3 vCPU）、
Node v24.19.0、Chromium 154.0.8037.57 で計測。
変更前は `8a9555c` に `findClashes:update` のベンチだけを追加したもの、変更後は本PRの実装。
上のWindows PCとは環境が違うため、#92の54.0msと今回の値を直接比較しない。

### 更新方法と結果の一致

- `findClashes(layout, previous)` で `worldTracks` の差分共有を使う。`changedPieces` が変更なしとしたトラックの判定用形状（逆行列・サンプル点・境界箱）を再利用する。
- トラック対の干渉点と双方向の最小クリアランスをWeakMapで保持する。「干渉なし」も保持し、接続や先行する干渉によって省略した判定は、必要になった時点で計算する。変わったトラックに関わる対だけが新しくサンプル点を調べる。
- 接続状態は毎回確認する。従来と同じトラック順で結果を組み立て、ピース対の重複除去、最小隙間と同値時の位置、干渉がある対のクリアランス除外、結果の並び順を保つ。境界箱の対の走査自体は引き続き全組み合わせを行う。
- キャッシュのキーはトラック・判定用形状への弱参照とし、過去のLayoutを保持しない。返す座標はコピーし、呼び出し側で変更してもキャッシュを壊さない。

既存の `performance.test.ts` と `clash-bounds.test.ts` のスナップショットは変更していない。
`incremental.test.ts` のS/M/Lの編集列に干渉判定の比較を追加した。
密集した3つの固定seedでも、色・ねじれ・長さ・反転・移動・途中の削除・逆更新について全体計算と座標・順序が一致する。
接続だけが変わる場合、干渉とクリアランスの切替、干渉の解消、キャッシュなしの初回、返却座標の変更も検証する。
