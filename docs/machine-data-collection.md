# 公式パーツ情報の収集・分類・抽出案（Issue #30）

作成日：2026-10-27（日本時間）。この文書は会話で検討した自動化案の記録であり、スクレイパーやAPI処理を実装・実行済みという意味ではない。[現時点の実データ](machine-parts.md)、[抽象化・組立方針](machine-assembly.md)、[Deep Research照合](machine-research-review.md)を前提とする。

## 収集範囲

[公式パーツ一覧](https://www.tamiya.com/japan/products/list.html?genre_item=3030)からページ送りと製品ページのURLを取得する。2026-10-25の確認時点では633件・1ページ20件だったが、この件数を固定値として巡回しない。キット・シャーシの基礎諸元、規則、カタログの適合注記は別の出典として収集する。

品番・URL・製品名・公式タグを通常のHTML処理で取得し、ナビゲーションを除いた製品本文を抽出する。取得日時・本文ハッシュ・取得成否を記録し、保存した本文を使って抽出を再実行できるようにする。再取得は低頻度・差分中心にし、取得失敗を空の製品情報として上書きしない。サイトの利用条件・取得条件を確認して運用する。

## プログラムとモデルの分担

| 処理 | 担当案 |
| --- | --- |
| ページ送り、URL列挙、品番等の定型欄 | 通常のプログラム・HTMLパーサー |
| モーター／タイヤ／ローラー等の大分類 | 公式タグを優先。不足する分類にDecisions APIを利用 |
| 説明文から寸法・重量・材質・取付条件を抽出 | GPT-6 LunaをResponses APIのStructured Outputsで使用 |
| 単位変換、範囲検査、重複排除、既存データとの比較 | 通常のプログラム |
| 出典が矛盾する値・意味が曖昧な条件 | 確認待ちへ。必要なら人または別のモデルで再検討 |

[Decisions API](https://developers.openai.com/api/docs/guides/decisions)は真偽条件・選択肢からの分類・スコア評価に使う。独自JSONのフィールド抽出には[Responses APIのStructured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)を使う。GPT-6 Lunaはモデル、Decisions／ResponsesはAPIの選択であり、互いに同列の代替モデルではない。

全件を両APIへ二重に送ることは必須にしない。まず構造化抽出と公式タグで足りるかを確認し、不足する分類にだけDecisionsを追加する。使用モデル・プロンプト・抽出スキーマの版も記録する。

## 抽出する事実と条件

値だけでなく、単位、値が指す対象、1個／2個／セットの別、概数か、測定・掲載条件、根拠の本文箇所、出典URLと確認日を持つ。未掲載は `null` とし、推測値を公称仕様に混ぜない。単位変換・1個当たりへの換算等の派生値は、元の値と計算方法を別に残す。

特に次の誤認を検査する。

- タイヤ外径と裸のホイール径。
- ローラーの径・本体厚みと、マシン上の取付高さ。
- 2個の合計重量と1個の重量、ウエイト単体とビス等を含む機構全体の重量。
- モーターの推奨負荷トルク時の回転数と、無負荷回転数・停止トルク。
- シャーシの電池装着時の構成例と、裸のシャーシや任意の完成車の重量。
- 「装着可能」と「無加工で装着可能」、部品全体の使用可否と同梱品の一部だけの適合。
- 同一品番での仕様変更、公式訂正と古いカタログ・口紙の表記。

抽出結果は原資料の事実として保持し、そこから性能タイプへ分類する。色や意匠違いを同じ性能タイプへまとめても、元品番の参照・適合条件・既知の質量差を失わない。ステーの穴座標など、本文にない幾何はAIで補完せず、図面または実測を必要とする。

## クラスの判定

「ストック／オープン」を製品単体の二択ラベルにしない。未加工の純正製品は共通の基礎データとし、加工個体は元製品・加工内容・加工後の実測を別に保存する。組立後の適合は規則の版と、部品・取付け・加工履歴・寸法・可動範囲から検査する。抽出や分類の確信度は、規則への適合保証ではない。

## 最初の評価

まずモーター・タイヤ・ローラー・ダンパー等から30〜50製品を選ぶ。既存104行を照合の手掛かりにしつつ、正解は原ページを確認して作る。分類精度、フィールドごとの抽出誤り・欠損、根拠との一致、単位・対象の混同、例外条件の取りこぼし、処理費用を測る。既存CSV自体も誤りがない前提にせず、食い違いをレビューする。

合格した抽出結果を既存CSVへ反映し、確認待ちを分ける。比較の前にAPI費用や所要時間を確定値として見積もらず、試行の実績から全件処理の計画を決める。PDF図表の読取失敗やネットワーク上の取得制限は、モデルの分類・抽出とは別の問題として扱う。
